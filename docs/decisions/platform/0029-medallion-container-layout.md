# ADR-0029: Five-Layer Medallion Container Layout (landing/raw/base/enriched/curated)

**Status:** Accepted
**Date:** 2026-04-24
**Deciders:** Michael Bendfeldt
**Scope:** Databricks / Lakehouse data layout

## Context

A Databricks lakehouse on ADLS Gen2 uses a **container-per-layer** model
to separate raw landed data, conformed data, and curated marts. Unity
Catalog also expects an external location per "logical layer" so grants
can be issued per layer (ADR-0030).

The classic Databricks medallion is three layers (bronze / silver / gold).
On real engagements, that compresses too many distinct responsibilities
into "silver" and "bronze" — landing-zone vs. immutable raw vs. typed
have different ownership, retention, and grant profiles.

## General Principle

When a three-layer medallion is **insufficient to express distinct
responsibilities, retention, and grants**, prefer a **five-layer model**
that separates landing, raw, base, enriched, and curated. The number of
layers is a function of the engagement; the structural pattern (one
container per layer, one Unity Catalog catalog per container) is the
constant.

| Layer    | Role                                                       |
|----------|------------------------------------------------------------|
| landing  | Drop zone for ingest tools (ADF, Event Hub, file arrival)  |
| raw      | Immutable, schema-on-read copy of source data              |
| base     | Typed/cleaned copy with a stable schema                    |
| enriched | Joined/derived datasets, business rules applied            |
| curated  | Consumption-ready (semantic-model / API / BI)              |

Choose layer names once and never rename — every external location,
catalog, and grant is keyed off the name.

## Technology-Specific Application

Drive the layout from a single list variable so the storage container,
external location, catalog, and grants are all generated by `for_each`:

```hcl
variable "container_list" {
  type    = list(string)
  default = ["landing", "raw", "base", "enriched", "curated"]
}

resource "azurerm_storage_container" "lakehouse_layer" {
  for_each              = toset(var.container_list)
  name                  = each.value
  storage_account_name  = azurerm_storage_account.lakehouse.name
  container_access_type = "private"
}
```

The same list drives:

- Databricks `external_location` resources (one per container).
- Databricks `catalog` resources (one per container, named
  `${project_name}_${layer}_${environment}`).
- Per-layer grants on those catalogs.

### Trade-offs in this realisation

- Renaming a layer mid-life is a destructive change — containers,
  external locations, catalogs, and all grants get recreated.
- Adding a layer at the end is safe; inserting a layer in the middle
  changes the `for_each` keyspace for downstream resources and recreates
  them.
- Five layers is more than some smaller engagements need; `base` and
  `enriched` may functionally collapse, but the structure stays.
- The layout does not enforce that pipelines tag which layer they wrote
  to — that remains a code-review and pipeline-template concern.

## Alternatives Considered

### Alternative A: Three-layer bronze/silver/gold
- **Pros:** Industry-standard naming; matches Databricks marketing.
- **Cons:** Conflates landing-zone vs. immutable raw vs. typed;
  conflates enriched vs. curated; harder to reason about lineage and
  ownership in non-trivial engagements.
- **Rejected because:** The three-layer split breaks down in practice
  on engagements with real ingestion variety. Use it where it
  genuinely fits; default to five.

### Alternative B: Single container with prefix-based "layers"
- **Pros:** One firewall rule, one external location, one credential.
- **Cons:** Cannot grant per layer; cannot apply per-layer lifecycle /
  retention; blast radius of a misconfigured grant is the entire lakehouse.
- **Rejected because:** Loses the Unity Catalog per-location grant model.

### Alternative C: One storage account per layer
- **Pros:** Strongest per-layer blast-radius isolation.
- **Cons:** Five times the network rules, RBAC, and monitoring.
- **Rejected because:** Single-account is the chosen storage baseline
  (ADR-0028); revisit when PII isolation requirements harden.

## Consequences

- A `for_each = toset(var.container_list)` pattern means adding a layer
  is a single tfvars change.
- Per-layer Unity Catalog catalogs make per-layer RBAC trivial (e.g.,
  "developers cannot write directly to `curated`").
- The naming convention `${project}_${layer}_${env}` is parseable in
  BI / lineage tools.
- Per-layer catalogs allow per-layer access policies — useful for GDPR
  data-classification mapping (curated may carry derived PII; raw may
  carry source-system pseudonyms).
- Layer naming is essentially permanent; pick once.

## Related

- ADR-0030 — Unity Catalog external locations and catalogs driven by the
  same list.
- ADR-0009 — Five-layer data architecture (toolkit-level baseline this
  container layout realises in storage).
- ADR-0016 — Unity Catalog catalog/schema structure. Note: ADR-0016 was
  authored against the classic three-tier (bronze/silver/gold) vocabulary
  at the **schema** level, while this ADR prescribes a five-layer split
  at the **container** level. UC schemas may map many-to-one onto the
  underlying container layers (e.g. UC `bronze` schema reading from
  `raw` and `base` containers). Engagements adopting the five-layer
  container model should consider whether to expose all five at the
  schema level too, or keep the schema layer aligned with the
  classic three-tier presentation.
